# dsh-agent-checkin

> DeepSeek Harness 的每日签到聚合 + 模型接入插件 —— 一个插件，三件事。

[English](README.md) | 中文 | [Español](README-es.md) | [Português](README-pt.md) | [हिन्दी](README-hi.md)

## What it does

这个插件把本机已经安装好的 AI 客户端，用三种方式接进 DeepSeek Harness（DSH）：

1. **签到聚合** —— 对全部支持的平台跑一轮签到，把每个平台的结果**和**实时积分余额
   汇总到一处。
2. **本机客户端作为模型 provider** —— 读本机已登录的 AI 客户端模型目录（TRAE、Qoder CN、
   WorkBuddy、百度搭子 DuMate、WPS 灵犀），把它们注册成 provider，让模型出现在模型
   选择器里、可以直接聊天。
3. **模型接入** —— 把兼容 OpenAI 或 Anthropic 的端点注册成 DSH 的 provider 路由。

三半读的是同一批本机客户端：看板里的余额和选择器里的模型，属于同一批账号。

**Token 用量面板**是第四个、独立的界面：它读 DSH 自己的会话日志，报出每个 provider / 模型
消耗了多少 token，并在最下方给出**模型权威排名与任务推荐**（能力分数取自公开榜单，
「有哪些模型」只看本机）。它和上面三件事都不相干——见「[Token 用量面板](#token-用量面板)」。

> **当前完成度（v0.8.0）**：①签到聚合**已完成可用**；②本机客户端模型接入
> **已扩到五个平台**——TRAE（国内/国际）、Qoder CN、WorkBuddy（国内/国际）、
> 百度搭子 DuMate、WPS 灵犀统一走 `lib/connect/` 五层架构（本机凭证 → 模型目录 →
> 回环 shim → PiAiAdapter → 注册）；「接哪些平台、每个平台显示哪些模型」在
> **设置 → 签到聚合 → 平台与模型**页签里选（「全部模型」跟随清单，或「我自己挑」
> 直接点要用的），每个模型后面带客户端给的倍率，保存即生效、不用重启；
> ③**Token 用量面板已完成**——侧栏「Token 用量」入口，读 DSH 自己的会话日志，
> 按 provider / 模型统计四段 token、调用次数与缓存命中率（含趋势、来源分布、排行、明细表），
> 输入框左侧另有当前 provider 的积分余额徽标；面板最下方还有**模型权威排名与按任务类型的
> 推荐**（能力分数取自公开榜单 Artificial Analysis / OpenRouter，「有哪些模型」只看本机清单
> 与你的勾选——**进榜不等于你已订阅**）；④`modelRoutes` 那半边代码可用，
> 但只支持静态 `apiKeyEnv`、且不支持 `headers`，当前 profile 里也没配任何路由。
>
> **PhanthyWork 不可接入（已实测）**：其反向代理端口 3456 始终不监听，真实凭证只
> 存在于主进程内存，无旁路可走。

## Requirements

- DSH `0.2.x`。
- `PATH` 上有 Python 3.9+（仅签到那一半需要）。
- Node 22.19+ 或 24+，且带内置 `node:sqlite` 模块（仅 `traeProvider` 需要）。
- 引擎本身已经**内嵌**在本包的 `engine/` 里，无需额外安装。如果你自己维护了一份引擎检出，
  把 `homeDir` 指过去即可。

## Installation

```bash
dsh plugin install ./dsh-agent-checkin
```

或者手工加进 profile：

```yaml
# ~/.dsh/profiles/<name>/cordis.patch.yml
- insert:
    - id: dsh-agent-checkin
      name: dsh-agent-checkin
```

## Usage

### 签到

| 入口 | 用法 |
| --- | --- |
| 命令 | `/checkin` —— 全部平台跑一轮 |
| 命令 | `/checkin trae,dumate` —— 只跑列出的平台 |
| 命令 | `/checkin --force` —— 绕过当天的幂等保护，强制重新领取 |
| 命令 | `/checkin-status` —— 查看上一轮结果，不重新执行 |
| 工具 | `checkin_run` —— 同一件事，可由 agent 调用 |
| 设置面板 | 「立即签到」按钮 —— 点一下跑一轮，跑完逐平台显示结果 |
| HTTP | `GET /dsh-agent-checkin/status` —— 给看板用的 JSON 快照 |
| 浏览器 | `GET /dsh-agent-checkin` —— 人类可读的看板页面 |

**默认不领取任何东西。** 插件出厂是 `allowClaim: false`，会把每一轮都强制降级为只读核对。
真正改变账号余额的签到是对现实世界的操作，必须显式开启：

```yaml
- id: dsh-agent-checkin
  name: dsh-agent-checkin
  config:
    allowClaim: true
```

也可以直接在宿主的**插件设置面板**里改——`allowClaim`、`pythonCommand`、`homeDir`、
`timeoutMs`、`pushResult` 这五个字段是 hot-reload 的，改完下一次运行立即生效，不用重启。

插件设置面板里那个「实时领取」开关是**真的能改**的：它通过宿主的 `configEditor` 服务把新值写回
你的 profile `cordis.patch.yml`（加文件锁、校验、原子写、失败回滚），再靠上面这套 volatile 热提交
让运行中的实例立刻读到新值。所以点一下开关就够了——既不用手改 YAML，也不用重启。写失败时面板会
显示服务端给出的真实原因，不会装作成功；如果本来就是那个值，它会明说「什么都没做」。

### 看板

在运行 DSH 的这台机器上打开 `http://127.0.0.1:<端口>/dsh-agent-checkin`。它只在回环地址上提供：
`Host` 或 `Origin` 不是本机回环的请求一律 403，所以同机其它程序（或经 DNS rebinding 伪装的外部
页面）读不到你的余额。

页面遵守与命令输出同一套诚实性规则：

- **只读这件事写在最上面。** `allowClaim: false` 时页面顶部直接说明本轮没有领取任何积分。
- **只读平台单独一节。** 没有领取接口的平台永远不会被算进「签到成功」，因为压根没有这个动作。
- **不出现跨平台总额。** 积分、credits、灵感值是不同币种，加起来得到的数字没有意义。页面写明
  这一点，而不是给出一个数。
- **余额未知显示 `—`，不显示 `0`。** 0 是一个读数，「没读到」不是。
- **读到了就必须显示出来。** 各平台的可用余额藏在不同的字段名下（千问是三档额度的合计，
  TRAE 与 WorkBuddy 国内版是 `total_credits`），归一化集中在引擎的 `bridge.py` 里；
  插件侧再兜一层，所以你即使把 `homeDir` 指向自己那份没有该补丁的旧引擎，余额也不会显示成
  「未取到」。
- **每个数字都标来源**：本轮实时拉的、从状态文件读回的、还是没有。
- **平台风险写在页面上。** 设备号指纹一类的提醒出现在页面底部，而不是只躺在源码注释里。

`/dsh-agent-checkin/status` 返回同样的数据，给脚本用。

看板底部还有一个入口：**模型接入（选平台 / 选模型）** → `/dsh-agent-checkin/models`，
在那里选哪些平台、哪些模型出现在 DSH 的模型选择器里（保存立即生效）。这页是**没有设置界面时
的等价入口**；平时请用设置页里的「平台与模型」页签（两边读写同一份选择文件）。细节见
「[模型接入：把本机客户端变成模型 provider](#模型接入把本机客户端变成模型-provider)」。

### Token 用量面板

设置侧栏最下面、内置分区之后还有一个入口：**Token 用量**。它不在设置面板里，而是一个独立的
主区面板——点侧栏那个图标就打开。

面板统计的是**本机所有 workspace、所有会话**的模型消耗，数据源是 DSH 自己写的会话日志
（`$DSH_HOME/sessions/`），不是本插件的签到结果，所以它和签到那半边完全独立：不签到也能看，
签到失败也不影响它。

- **七个统计卡**：累计消耗、今日、近 7 天、调用次数，加上缓存命中、缓存未命中、缓存命中率。
  调用次数那张卡的副标题还给出「几个来源 · 几个模型」——**来源数不等于模型数**，一个 provider 下
  往往挂着几十个模型，这两个数分开报才不至于让人把「接了 11 个来源」误读成「只有 11 个模型」。
- **三个缓存指标的口径**（写在卡片提示里，也写在这里）：**命中 = `cacheRead`**；
  **未命中 = `input + cacheWrite`**；**命中率 = 命中 ÷（输入 + 命中 + 写入）**。分母**不含输出**——
  输出 token 永远不是缓存候选，把它算进去会让命中率凭空变好看。分母为 0 时显示「—」而**不是 0%**：
  0% 是一个读数，「没有可算的分母」不是。这三个指标与「累计消耗」同基准（全时段），
  不随时间窗变化——要按窗口算需要后端把每日归桶也扩成四段，那是另一件事。
- **时间窗可切**：7 天 / 30 天 / 90 天 / 全部。切换只改展示范围，不重新扫描——
  扫描器一次性把全部历史归好类，窗口是切在结果上的。
- **三张图并排一行**：消耗趋势（可在「每日」与「累计」之间切）、来源分布（环形图，取前 6 个来源）、
  模型使用排行（取前 8 个模型）。趋势图宽度按三分之一栏宽设计（坐标宽 360，不是早期那版 640——
  640 在三分之一栏里会把右侧刻度压得看不见）。
- **按来源明细表**：逐行列出每个 provider / 模型组合的四段用量、调用次数，以及三个由同样数据
  当场算出的效率列——**命中率**、**均次消耗**（合计 ÷ 调用次数）、**输出占比**（输出 ÷ 合计）。
  后两列用来分辨「贵但一次干完」和「便宜但来回试」。
- **页脚如实报扫描代价**：扫了多少个会话文件、多少 MB、本次重扫了几个、多少条计费消息、
  耗时多少毫秒。**本次因超时没扫完时会明写「本次因超时未扫完」**，不把半份数据装成完整结果。

HTTP 端点 `GET /dsh-agent-checkin/usage` 返回同一份数据，给脚本用：

| 参数 | 含义 |
| --- | --- |
| `days=7` | 时间窗（天）。省略则用默认窗；`3650` 表示「全部」 |
| `refresh=1` | 绕过内存缓存强制重扫 |

端点与插件其余路由同一套守卫：只接受本机回环请求（非回环一律 403），只接受 `GET` / `HEAD`，
响应一律 `cache-control: no-store`——「刚刷新完还是旧数字」是这类面板最伤信任的失败模式。

#### 数字是怎么算出来的

这一块值得写清楚，因为它踩过四个**会静默算错**的坑：

- **一个会话日志是「多帧 zstd」，不是一帧。** 实测一个 `session.v4.jsonl.zstd` 里是 **12829 个**
  独立 zstd 帧首尾相接；直接调 `zstdDecompressSync` 只解第一帧，**其余 99% 的内容会被静默丢掉**，
  而且不报错。所以扫描器逐帧切分（按 zstd 魔数 `0xfd2fb528` 找边界）再逐帧解压。
- **`assistant/attempt` 的用量是重复的。** 同一次调用会在 `attempt` 与 `message` 两处各记一遍
  usage（`attempt` 的只出现在 `data.stream[].chunk.usage` 里，与最终 `data.usage` 是同一份），
  两处都算会让总量凭空翻倍。扫描器**只认 `assistant/message`**，`attempt` 用于去重与关联，不进计数。
- **`totalTokens` 字段是旧口径。** 它恒等于 `inputTokens + outputTokens + cacheReadTokens +
  cacheWriteTokens`（用 8129 条记录核对，7952 条精确吻合，余下 177 条是旧版本记录缺
  `cacheWriteTokens`），而真正的「计费输入」是 `input + cacheRead + cacheWrite`。所以页面显示的
  总量一律**按四段求和**，不读那个现成字段——不能指望它一直是新的。
- **同名会话同时存在多个版本时只读最高版本**（`session.v4.jsonl` 与 `session.jsonl` 并存），
  否则同一份用量会被数两遍。

#### 增量缓存

日志只增不减，所以缓存策略是「内存快照 + 按文件失效」：记下每个会话文件的 `size:mtime`，
下次只重扫变了的那几个。实测 44 个文件、9333 条计费消息的场景下，冷扫约 1.5 秒，
热扫约 150 毫秒。

缓存 TTL 由配置项 `usageCacheSeconds` 控制（默认 30 秒）。面板上的「刷新」按钮总是绕过缓存重扫，
这个值只影响自动轮询与其它调用方。**不引入数据库**：43 个日志 / 48 MB 冷扫 1.3 秒，
而日志只增不减，内存缓存已经能把日常刷新压到个位数毫秒；引入 SQLite 只会多一份需要迁移、
需要与日志对账的副本。

#### 输入框余额徽标

输入框左侧（`conversation.input.left`）还会显示**当前引用 agent 所用 provider 的积分余额**。
这里最要紧的是**不撒谎**：

- **平台真有「积分余额」这个概念时才渲染**（比如 WorkBuddy）。后付费的 token 计费平台没有
  这种东西，硬编一个数字出来就是撒谎——所以那种情况下**整个徽标不渲染**，也**不拉起任何轮询**。
- **余额未知就整个不出现**，不显示 `0`。0 是一个读数，「没读到」不是。
- **悬停显示来源**：这个数字是「实测」还是「手动录入」写在 `title` 里，两者绝不混同。
- **轮询很稀**：余额按天变，一分钟一次已经远超需要。
- **与 `dsh-connect-workbuddy` 共存**：老插件也占用这个 slot（order 4，只对自家 provider 渲染），
  本插件 order 5 紧随其后，两者靠「只认自己认识的 provider」区分，不会同时冒出两个徽标。

#### 面板的错误边界

用量面板外面套了一层 React 错误边界（class 组件——`getDerivedStateFromError` 是类专有的，
函数组件没有等价物）。**为什么必须有**：`main` slot 里的组件一旦在渲染期抛异常，宿主会把整个
面板渲染成空白或回退，而**浏览器控制台里那行错误用户看不到**（桌面版没有 devtools 入口），
表现就是「点了侧栏按钮什么都没发生」。有了这个边界，同一个故障会变成页面上的一行红字，
用户能直接把原因读给维护者。

排名区**另外**套了一层自己的边界：榜单拉不到不该把上面的用量统计一起变成空白，
这两件事的失败原因毫不相干。

#### 模型权威排名与任务推荐

面板最下方还有一段：**模型权威排名**，以及按任务类型的推荐。它由两部分拼成，来源严格分开：

- **能力分数来自公开榜单**——Artificial Analysis 的智能 / 编码 / 智能体指数，经 OpenRouter
  公开接口（`https://openrouter.ai/api/v1/models`，免鉴权）取回。**本插件自己一个分数都不估**：
  本机客户端目录里只有 id、名字、倍率和是否支持图片，**没有任何质量维度**，按名字猜强弱就是编。
- **「有哪些模型」只看本机**——只列本机客户端清单里真实存在的模型（当前登录的那个区），
  并已套用你在「平台与模型」里的勾选。榜单里有、本机清单里没有的模型一律不进榜：
  排名是给「我现在能用什么」用的，不是给「世界上有什么」用的。

**必须说清楚的一件事**：客户端目录是**产品名册，不按账号订阅过滤**。实测未订阅的
`workbuddy-global` 账号，目录里照样有 `gpt-6-astra` / `gpt-5.4` 这些 GPT 系列模型。
所以**某个模型进榜，不等于你的账号有权调用它**——这句话原样印在面板上，不假装排名等于订阅权益。
面板也没有本事自动判定订阅：各平台目录里**没有任何权益字段**（对 WorkBuddy 目录全量 grep
`vip|subscrib|entitle|tier|quota` 只命中注释里的一处「免费模型」说明）。真的调用不了时，
平台的错误会照常露出来，那才是权威信号。

面板内容：

- **总榜**：按智能指数降序，最多 12 行，每行给出可用平台、智能 / 编码 / 智能体指数、
  上下文窗口、每百万输入 token 价格，以及客户端给的倍率（倍率用 `x` 前缀标出，
  免得被当成分数的一部分）。
- **按任务类型推荐**，六类：写代码、推理与数学、智能体与工具调用、长文档、多模态（看图）、快而省。
  **每张卡把自己的排序规则原样写在卡上**，让「为什么它排第一」可以当场复算：
  - 写代码 → 按编码指数降序，没有编码指数的用智能指数兜底；
  - 推理与数学 → 按智能指数降序；
  - 智能体与工具调用 → 按 agentic 指数降序，没有的用智能指数兜底；
  - 长文档 → 按上下文窗口降序；
  - 多模态 → 只取支持图片输入的模型，按智能指数降序；
  - 快而省 → 只取智能指数 ≥ 40 的模型，按每百万输入 token 价格升序。
    **40 这个门槛是故意的**：智能指数低于它的便宜模型不配叫「省」，只是弱。

两个数字口径值得单独讲，因为它们是同一类错误的反面教材：

- **「没有这个指数」与「这个指数是 0 分」是两回事。** 榜单对缺失的指数发的是**显式 `null`**
  （实测 `anthropic/claude-haiku-5.5` 的 `coding_index` 就是 `null`），而 `Number(null)` 是 `0`。
  早期写法直接 `Number(value)`，于是 **98 个没有编码指数的模型被当成「编码 0 分」**，
  在写代码榜里排到真·弱模型前面。现在 `null` 一律保持 `null`，页面显示「—」。
- **没有智能指数的模型沉底，不当 0 用**。总榜排序时 `null` 排在所有有分数的模型之后，
  而不是混在低分段里。

排名失败**不是**致命错误：手上有旧榜单就继续用它，并在页面上标「本次刷新失败，下面是上次成功
拉取的榜单」加上失败原因。只有「从来没成功过」才显示失败——那时也必须说明**为什么没有排名**，
而不是画一张空表让人以为本机没有可用模型。反过来，榜单读到了但一条都没匹配上，也不是错误而是事实，
面板会明说「本机可用模型（N 个）在榜单里一个都没匹配上——可能榜单还没收录这些新模型」，
并列出没匹配上的那些名字，供你判断是榜单缺条目还是名字对不上。

榜单缓存与用量扫描器同一套路：内存快照 + 磁盘兜底（`$DSH_HOME/dsh-agent-checkin/model-rank.json`）
+ 并发请求串行化。TTL 6 小时——榜单以天为单位变，刷太勤只是白费网络。

HTTP 端点 `GET /dsh-agent-checkin/model-rank` 返回同一份数据；`?refresh=1` 强制绕过缓存重拉榜单。
守卫与 `/usage` 相同（只回环、只 `GET`/`HEAD`、`no-store`）。

### 设置面板

设置 → **签到聚合**（排在设置侧栏最下面，内置分区之后），不用命令行也能完成日常操作：

- **立即签到** 点一下就从面板触发一轮完整签到（等价于会话里的 `/checkin`），不用切去敲命令。
  - 按钮立刻回「这一轮已开始」；**`started` 只说明这一轮被接受了，不等于签到成功**。跑完后在按钮
    下方逐平台列出结果，成功与否以那张表为准（`ALREADY`「今日已领过」也如实显示）。
  - 这也是设置面板里**唯一会真实改变余额的操作**：按钮文案与副标题如实写明当前是真实领取还是
    只读核对（由 `allowClaim` 决定）；跑动中按钮禁用并显示「运行中」，重复点击不会起第二轮。
  - 「强制重跑」会忽略「今天已领过就跳过」的保护，会不会重复领取由平台自己决定——按钮旁边把这
    句话挑明了写出来，普通点击则永远不会重复领取。
  - 引擎起不来时，面板直接显示失败原因（不会把「没有结果」说成「没有失败」）；明细缺失时明说
    「这一轮没有逐平台明细」，不渲染一张空表冒充完成。
- **实测登录态（只读）** 逐个平台跑一次真实的只读接口，结果分「正常 / 未配置 / 失败」三档。
  这一步**不领取任何东西**，也不会因为开了 `allowClaim` 就变成领取。
- **一键登录** 四个平台各有「打开登录窗口」按钮，分两种形态：
  - **Cookie 型（WPS 灵犀、即梦）**：点下去在本机拉起一个独立的浏览器窗口，你在里面正常登录，
    插件自己把 Cookie 收下来、验证一次、通过才写盘。不用再开 F12 翻请求头复制 Cookie，也不用记
    命令行参数。
  - **profile 型（可灵 AI）**：这个平台的福利靠「以登录状态访问一次」来领，凭证是
    整个浏览器配置目录而不是一份 Cookie。点按钮同样弹独立窗口，你登录后**亲手关闭这个窗口**，
    关闭后插件才用只读核验跑一遍登录态，通过才算数。
  - 这个按钮是**普通按钮，点下去发一个 POST**，页面不会跳走，宿主界面也不会被顶掉。这一点值得
    写清楚，因为前两版设计都栽在这里：用链接在主标签里打开（`target: '_self'`）会整个顶掉宿主
    界面，用链接开新标签（`target: '_blank'`）在这个 Electron 壳里根本弹不出窗口。
  - 面板发的请求**不带 `Origin`**，在这个宿主里是正常现象（DSH 宿主自己的判断也是「没有 `Origin`
    就放行」）。所以写接口的判据是：带 `Origin` 就必须同源、且指向本机这个回环端口；不带 `Origin`
    时只拒绝地址栏直敲那种（`Sec-Fetch-Site: none`）。其余来自回环的一律接受——能在本机伪造这种
    请求的人，本来就能直接读凭证文件。
  - **`started: true` 只说明采集窗口开了，不等于登录成功。** 面板每 2 秒轮询状态接口，按采集结果
    判定，绝不按「按钮有响应」判定。
  - 窗口用的是**独立配置目录**，看不到你日常浏览器的登录态——这是故意的：否则「已采集」可能
    只是从别的浏览器借来的会话。
  - 采集不到会等在后台，面板每 2 秒问一次进度，超时（默认 5 分钟）如实报超时，**不会**把超时
    记成成功。「取消」按钮只结束等待，措辞写明「登录没有完成」。
  - 全程没有成功标记就不算成功：进程退出码是 0 也一样。
  - 窗口打不开时，按钮下面直接显示服务端给的原因。这类失败只算「请求没成」，不会被记成一次
    登录失败。
- **手工凭证（备选）** 两个 Cookie 型平台（WPS 灵犀、即梦）也留着输入框，用来粘贴你自己抓的
  Cookie（例如自动化窗口起不来的环境）。保存后会立刻跑一次只读验证，结果显示在输入框下方——
  **「已保存」不等于「能签到」**，这两件事分开显示。保存成功后输入框立即清空，凭证不会在页面
  上多留一秒。profile 型的两个平台没有输入框可给：它们的凭证不是一份 Cookie，粘贴没有意义。
- **其余六个平台没有登录按钮也没有输入框**，每个都附一句原因（凭证在客户端本地加密存储，或者
  压根没有可调用的领取接口）。这里不给入口，是因为给了也没有用，不是忘了做。
- **各平台当前积分，实测优先、可手动补记。** 逐行列出每个平台当前显示的积分：引擎上一轮实测读到的
  值标「实测」（并注明来自哪个接口字段）；引擎读不到的平台（比如没有余额接口的）可以手动填一个
  当前值，标「手动」并可选附一句备注。手动值只是你自己的记录数字，**不是充值**，也永远不会冒充
  实测值——下一轮真的实测到时，实测值自动优先。
- **余额逐行列出，不提供合计。** 与看板和命令输出同一口径：不同平台是不同币种，加起来的数字没有
  意义。
- **真实领取开关是真的能改的。** 点下去会写回 profile 的 `cordis.patch.yml` 并立即生效，不需要
  重启；写失败时显示服务端给的真实原因，本就是这个值时明说「什么都没做」，都不假装成改成功了。
- **页签「平台与模型」：选平台、选模型，就在这个设置页里。** 每个已接入的平台一张卡片，勾上
  「在模型选择器里显示这个平台」，然后二选一：
  **「全部模型（跟随客户端清单）」**——客户端以后新增模型自动出现；
  **「我自己挑」**——从空白开始，你点哪个就只有哪个，存在显式清单里。
  切到「我自己挑」后可以「全选 / 全不选」，所以「只要 3 个」是 1 次「全不选」+ 3 次点击，
  不用先全选再一个个取消。点「保存」立即写盘并刷新 DSH 的模型选择器，**不用重启宿主**；
  服务端回的行数据是页面唯一事实来源，保存后页面按回包重画，`changed` 为空就如实说「没有变化」。
  未接入的平台也列出来，并写明原因——「以为它开着」比「明确说没接入」更浪费时间。
- **勾选行是可点的方块按钮，不是原生复选框。** 宿主设置面板里原生 `<input type="checkbox">`
  出现过「点了状态不变」，所以勾选态改由 state 决定：点一下立刻变，且只影响你点的那一行。
- **每个模型后面显示客户端自己给的倍率。** WorkBuddy 取清单里的 `creditMultiplier`（`0.79x`
  ＝打 79 折积分）、Qoder 取 `priceFactor`（`0` 显示「免费」）、TRAE 取嵌套的
  `features.consumption_rate.data.rate`（活动价 `activity_discount.data.current.consumption_rate`
  优先）；客户端没给的模型那一列就**空着**——页面上不留猜出来的数字。
- **图片输入也是逐模型可选的，而且与「显示哪些模型」互不牵连。** 卡片下半部分单独一块「图片
  输入」，有三档：**跟随原生能力**（默认——目录说这个模型支持图片就允许，客户端以后新增的多模态
  模型自动能收图）、**我自己挑**（逐个点，存显式清单）、以及一次点掉「全部关掉」或「全部打开」。
  只勾「显示」不勾「图片」的模型照常出现在选择器里，只是不能收图；反过来，目录没声明支持图片的
  模型也可以手动勾上——**上游到底认不认，以实测为准，插件不替上游下结论**。这块与平台开关、
  模型白名单是三条独立存储，关掉平台不会顺手丢掉你勾好的图片设置。
  - 浏览器看板 `/dsh-agent-checkin/models` 上对应的是模型行右边那个「图片」复选框，语义相同。

这一步需要宿主进程去 spawn Python、读文件，所以全部发生在宿主侧；浏览器那一侧只发 HTTP 打
`/dsh-agent-checkin/settings` 的子路由。凭证从头到尾没有经过前端，也没有出现在任何日志里——落盘后只回
字段名，不回值。登录进度回报里同样不含进程号。

### 幂等与结果持久化

每一轮成功的结果会写入 `$DSH_HOME/dsh-agent-checkin/last-run.json`，并且**当天已经成功领取过的平台不会
被重复领取**（按本机自然日）。这很重要——领取接口是真实的网络请求，误发一次 `/checkin` 不该变成
真的多打一次。

- 保护粒度是**每个平台每天一次**，且只认「有领取动作的平台」上的 `OK` / `ALREADY` / `DONE`。
- **失败从不被记住**——失败的平台可以立刻重试。
- **演练不设置保护**——演练什么都没领，不能当作「今天已领过」的证据。
- `/checkin --force`（或 `checkin_run` 传 `force: true`）可以绕过；这个口子必须是**显式**的，
  不能悄悄来。
- 全部平台今天都已完成时，本轮会报告 `source: skipped` 并**不发任何请求**。这是第三种结果，
  既不是成功也不是失败。
- 状态文件只写**白名单**里的展示字段。Cookie、token、JWT 一律不落盘。
- 状态文件读不出来或版本不认时会被忽略而不是照信，本轮就当首次运行处理。

### 每日自动签到

| 命令 | 用法 |
| --- | --- |
| `/checkin-schedule on 09:00` | 在当前会话开启每日定时（时间可省略，默认 09:00） |
| `/checkin-schedule off` | 关闭 |
| `/checkin-schedule status` | 查看当前定时状态与实际生效时间 |

定时任务挂在宿主的 Schedule 服务上，**每天按你本机的钟表时间触发**。开启后，每到点当前会话会
收到一条提醒，让模型调用 `checkin_run` 跑一轮并汇报结果。

插件对这条链路只承诺它真能保证的事：

- 宿主保证的是「提醒被投进本会话收件箱」，**不保证到点立刻唤醒模型**。会话空闲时，提醒会等你
  下次打开它时才被处理。
- 因此签到是在**模型收到提醒并调用工具**这条链路上完成的，不是插件自己在后台偷偷跑。
- 同一会话重复 `on` 不会叠出多条任务；`off` 只删本插件创建的那条，不会碰你在别处建的提醒。
- `allowClaim=false` 时定时照常触发，但那一轮仍然只会核对、不会领取——命令输出里会写明这一点。

想改成别的时间，再执行一次 `on HH:mm` 即可（会替换掉旧的）。

### 结果推送

`pushResult: true`（默认）时，`/checkin` 跑完会把结果摘要注入当前会话，供后续对话参考。
这里用的是 `agent.inject()` 而不是 `followup()`：**注入不会唤醒空闲会话**，内容在该会话下一次
请求时才可见。签到结果是「该知道但不该打断」的信息，所以不抢话。

推送失败（拿不到会话、宿主拒绝）只记一条 warn，不会把签到结果本身变成失败——你看到的是签到
的真实结果，不该因为附带推送没成功而被改判。

### 模型接入：把本机客户端变成模型 provider

插件启动时**一律尝试**把三个平台挂成 provider（本机没装、没登录、凭证解不开的平台自己跳过，
日志写原因，其余功能照常）。挂上之后，「显示哪个平台、显示它下面哪些模型」不再由重启宿主决定，
而是**在 DSH 的设置页里改**：

**设置 → 签到聚合 → 页签「平台与模型」**

（同页签「签到与凭证」是原来的签到配置；浏览器看板 `/dsh-agent-checkin/models` 仍然保留，作为没有
设置界面时的等价入口——两边读写的是同一份选择文件。）

- **平台开关**：关掉 = 该 provider 的模型从 DSH 模型选择器里消失；重新打开即恢复。
- **模型勾选**：「全选（跟随客户端清单自动增减）」或逐个点。取消「全选」再逐个点，存的就是显式
  子集；点单个模型只影响那一个。客户端目录新增模型时，全选的平台自动包含新模型。
- **倍率**：每个模型后面括起来的是客户端自己给的价格/积分倍率——WorkBuddy 的 `creditMultiplier`、
  Qoder 的 `priceFactor`（`0` 显示「免费」）、TRAE 的 `features.consumption_rate.data.rate`
  （活动价优先）。客户端没给的（如 TRAE 的自定义 base_url 变体），那一列空着，插件不猜。
- **保存立即生效**：插件写盘后 emit 一次 `llm/adapters-updated`，宿主的模型选择器当场重画，**不用重启宿主**。
- **选择存在本机**：`~/.dsh/dsh-agent-checkin/model-selection.json`（只有开关与模型 id，没有任何凭证）。

页面上的「已接入 / 未接入」是两种不同的状态，别混：

- **已接入**：provider 已注册进宿主。开关与勾选改完立即生效。
- **未接入**：卡片上直接写原因（没读到登录态、与老插件重名、宿主 pi 依赖不可用……）。
  要让未接入的平台出现，得先在本机客户端登录，然后重启宿主——**注册是装配期事实**：provider
  没注册过，模型选择器里就不可能有它的位置。这是协议的硬边界，不是插件偷懒。

> 老的 `traeProvider` / `traeIntlEnabled` / `qoderCnEnabled` / `wbProvider` / `wbProviderIntl`
> 已经**不再是开关**：它们只在选择文件还不存在时（升级后第一次启动）当一次种子，之后设置页里的
> 勾选才是权威。保留它们只是为了让你升级前的意图能迁移过来，不会丢。

#### 要不要开着客户端？（五个平台各不一样）

模型能不能用，取决于**凭据从哪来**，而不是「客户端开没开」。按凭据来源分三类：

| 平台 | 客户端要不要常驻 | 原因 |
| --- | --- | --- |
| **百度搭子 DuMate** | **必须常驻**（开着但可以不登录） | 它的模型网关是**本机** `dumate-main-server` 的随机端口，端口和 `X-Dumate-Inapp-Key` 每次启动都变。客户端关掉 = 没端口没 key = 模型必然不可用。**这是五个平台里唯一强制常驻的。** |
| **WPS 灵犀** | **不用开**（但 Cookie 要够新） | 模型接口是**云端** `lingxi.wps.cn`：建会话 `POST /api/aioffice/v1/sessions`、推理 `wss://…/completions/ws`，全程不碰本机任何端口。客户端只是**登录态的来源**——Cookie 是从客户端采集下来用的，采完就能关客户端。但 Cookie **三天过期**（`exp=259200`），到期要重新打开客户端采集一次。 |
| **WorkBuddy 国内 / 国际** | **不用开，但客户端要装着** | 模型接口也是**云端**（`copilot.tencent.com` / `www.codebuddy.ai`）。但 5.6.x 之后客户端把登录字段加密了（`$wbEncrypted`），解密密钥要由**桌面端二进制**用 `ELECTRON_RUN_AS_NODE` 交出来——所以 `WorkBuddy.exe` 必须在本机**可执行**（装着即可，不必运行）。 |
| **TRAE 国内 / 国际** | 不用开 | 凭据与模型目录都是**静态文件**（`storage.json` + `state.vscdb`），读一次就够。 |
| **Qoder CN** | 不用开 | 凭据是 Chromium OSCrypt 存储，经系统 DPAPI 在内存里解密，与客户端进程无关。 |

一句话：**只有 DuMate 强制常驻；灵犀要保证 Cookie 新鲜（不是保证客户端开着）；WorkBuddy 要保证客户端装着（不是开着）。**

> **灵犀 Cookie 放哪儿**：`<dshHome>/dsh-agent-checkin/engine/lx_cookie.txt`（推荐，重装插件不会丢）。
> 插件按 `LINGXI_COOKIE_FILE` 环境变量 → 该路径 → 包内 `engine/lx_cookie.txt` 的顺序找，
> 三个都找不到才算「未接入」，卡片上会写清找过哪些路径。

#### 三个平台各自读什么（全部只读，不回写客户端）

| 平台 | 登录态来源 | 模型目录 | provider id |
| --- | --- | --- | --- |
| TRAE 国内版 | `%APPDATA%\TRAE CN\User\globalStorage\storage.json`（解密后的 token、设备 id、用户 id、区域） | 同目录 `state.vscdb`，30 分钟 TTL 刷新 | `trae` |
| TRAE 国际版 | 国际版客户端的同名文件 | 同上 | `trae-global` |
| Qoder CN | Chromium OSCrypt 加密存储，经系统 DPAPI 在内存里解密，临时文件即取即删 | 客户端目录（缓存只存元数据） | `qoder-cn` |
| WorkBuddy 国内 / 国际 | 客户端登录态；token 临期刷新只发生在进程内存里 | 客户端 `/v3/config`，按国内/国际渠道分开 | `workbuddy` / `workbuddy-global` |

凭证除各平台自己的 API 域外不发往任何地方（TRAE 的域取自凭证本身，不是硬编码）。

注册后，TRAE 以 **Trae**（国际版为 **Trae Global**）出现在模型选择器里。TRAE 通道有三个特点
值得提前知道：

- **模型挂在哪个 `function` 上，决定它能不能调。** TRAE 的 chat 端点是
  `/api/agent/v3/llm_utils_chat`，请求体里除 `model` 还要带一个 `function`；**同一个模型只在
  某些 function 下存在**。插件从目录条目的 `appearedIn` 里按 `solo_work_remote` →
  `solo_work_lite` → `solo_agent_remote` → `chat_v3` → `solo_coder` 的优先级挑，挑不到就一律
  落 `solo_work_remote`，绝不把 `assistant` / `solo_agent` 这类不是 chat 入口的分类名透传上去。
- **不承诺全部可调：34 个可选模型里 30 个能调，4 个上游拒绝。** 2026-10-18 逐个发了最小真实
  请求，`deepseek//deepseek-v4-flash`、`deepseek//deepseek-v4-pro`（自定义 base_url 变体）、
  `kimi-k2.8-preview`、`qwen3.8-flash` 这四个穷举了所有候选 function 仍回 `4001`，判定为上游
  不服务（这两条 base_url 变体在客户端目录里有，但客户端自己也调不动）。同一个模型的可用
  function 也可能只有一个：`DeepSeek-V4-Flash-Official` 在 `solo_work_remote` / `solo_work_lite`
  / `solo_agent_remote` 通，`chat_v3` 回 `1005`（付费计划不覆盖）、`solo_coder` 回 `4001`。
  服务端随时可能改，插件不预先过滤。
- **响应是真流式，但帧是命名的，不是 OpenAI 形状。** 上游发 `event: output`（`response` /
  `reasoning_content` / `tool_calls`）、`event: token_usage`、`event: done` 三种帧，另有一堆
  `metadata` / `timing_cost` / `progress_notice` 记账帧。插件把 `output` 转成 OpenAI chunk 转
  发、`token_usage` 归一成 usage、`done` 转成 `finish_reason`，记账帧丢弃。所以文字是按字出现
  的，内部轨迹被隐藏。

> **更正一处旧说法。** 本 README 早前写过「目录里 34 个模型逐个请求全部 `HTTP 200`」，那是错的：
> 那批请求打的是 `/api/ide/v2/llm_raw_chat`（一个本机客户端根本不发的推断端点），拿到的 200 是
> GET 或非 JSON 请求上的错误帧。真实端点换成 `llm_utils_chat` 后，结论就是上面这条 30 / 4。

> **WorkBuddy 冲突指引**：本功能接管了老插件 **dsh-connect-workbuddy** 的模型接入。两个同时开会以
> 相同 provider id 抢注册位。请先关掉老插件：DSH 设置面板 → 插件 → dsh-connect-workbuddy →
> 关闭，重启宿主；关闭无效再卸载它。本插件遇到 id 冲突时会记一条 warn 并在看板卡片上说明，
> 不影响其它平台与签到。模型 id 与老插件**逐字一致**，已有的会话与配置可以直接迁移。

### 接入模型

在配置里声明一条路由：

```yaml
- id: dsh-agent-checkin
  name: dsh-agent-checkin
  config:
    modelRoutes:
      - provider: my-gateway
        displayName: My Gateway
        api: openai-completions
        baseURL: https://gateway.example.com/v1
        apiKeyEnv: MY_GATEWAY_API_KEY
        models:
          - id: some-model
            name: Some Model
            contextWindow: 131072
            maxTokens: 8192
```

然后落盘：

| 入口 | 用法 |
| --- | --- |
| 命令 | `/checkin-models` —— 把路由写进当前 profile |
| 工具 | `model_route_apply` —— 同上，先加 `dryRun: true` 可以预览 |

`api` 取值是 `openai-completions`、`openai-responses` 或 `anthropic-messages`。自己搭的路由
**必须**逐个列出模型 —— 宿主没有可回退的目录条目，没有模型的整条路由会被直接拒掉。

宿主提供 `configEditor` 时，落盘走它：这条路径保留 YAML 注释、原子写、失败回滚，并
重新加载配置。`configEditor` 不在时退化为直接改 profile patch，那种情况需要重启 DSH。

> **限制（尚未实现）**：`modelRoutes` 目前**只支持静态凭证**——`apiKeyEnv` 是一个**环境变量名**，
> 不是可以从客户端登录态动态获取的 token。所以凡是"凭证藏在某个桌面客户端里、要运行时才拿得到"
> 的上游，这条路径都接不了。另外它**还不支持 `headers`**（宿主 `PiAiProviderProfile` 有这个字段，
> 但本插件的 `modelRoutes` schema 和 `toProviderProfile()` 都没透出来，需要先补）。
> 详见 `模型接入路线-逐平台定案.md` §1 和 §3.4。

## Honest reporting

签到汇总刻意把四个数字分开：

- **成功** 统计 `OK` / `ALREADY` / `DONE`
- **中性** 覆盖 `DRY_RUN` / `READONLY` / `INACTIVE`
- **环境受阻** 覆盖 `SANDBOX_BLOCKED`
- **失败** 覆盖 `AUTH_REJECTED` / `FORBIDDEN` / `NETWORK` / `ERROR` / `EXCEPTION`

`READONLY` 的含义是「这个平台根本没有可执行的领取动作」。它不是成功；把它并进成功数，
既虚增了分子，又把一个不存在的动作伪装成已完成。汇总里另有一个 `healthy`：**确实存在
真实领取动作、并且跑成功了**的平台数。

`blocked` 单列，是因为有些失败跟平台毫无关系。解密本地凭证需要写一个临时密钥文件，适配器
因此会调 `tempfile.mkdtemp()` 再往里写。在 workspace-write 沙箱下，子进程能建目录却写不进
文件，解密于是抛 `PermissionError [Errno 13]`。上游适配器把它归成「凭证不可用」，而那句话
会把人引去重新登录——可重新登录根本解决不了沙箱限制。插件据此改判为 `SANDBOX_BLOCKED`，
保留原始报错以便追溯，并明说这是环境限制、不是凭证问题。只有「权限拒绝」**且**存在指向
运行环境的证据（临时目录路径，或沙箱自己点名）时才改判；凭证文件真的读不了、会话真的过期，
仍然如实报 `failure`。

余额从不跨平台相加。积分、credits、灵感值是不同币种，加出来的数字没有任何意义。

### 支持的平台

`workbuddy`、`workbuddy_intl`、`trae`、`lingxi`、`dumate`、`qwenwork`、`phanthywork` 有真实的
领取动作（`claiming: true`）。`jimeng`、`kling` 只是只读状态探针（`claiming: false`）
——如实报告账号里有什么，但插件从不替它们领取。

### 引擎会往哪里写

内嵌引擎住在插件安装目录里。两个适配器把手工填的 cookie 存在它旁边，浏览器自动化适配器也
在那里建临时 profile（`jimeng_cookie.txt`、`lx_cookie.txt`、`.<name>_profile/`）。npm 装出来
的包通常是只读的，所以要么把 `homeDir` 指向一份可写的引擎检出，要么预先在引擎能写的位置
放好 `jimeng_cookie.txt` / `lx_cookie.txt`，并接受浏览器自动化那类适配器（`jimeng`）会直接
失败、而不是半成品地静默跑过。任何碰真实凭证的东西都只落在那几个文件里，不出本机。引擎
作者自己的策略见 `engine/SECURITY.md`，自动签到的风险说明见 `engine/DISCLAIMER.md`。

### DuMate 的本地网关和它的临时密钥

DuMate 桌面端在一个随机本地端口上暴露 OpenAI 兼容端点，但每个请求都得带
`X-Dumate-Inapp-Key` 头，其值是进程启动时生成的 32 字节随机十六进制串，通过环境变量注入给
渲染层和子进程，**每次重启都会变**。

这个值确实不在任何配置文件里，但**它会被打进日志**——客户端自己的运行日志：

```
log\electron.log        DUMATE_INAPP_KEY: '<64 hex>'
log\desktop-main\Main.log
  [OPENCODE PROXY] ... headers: map[ ... X-Dumate-Inapp-Key:[<64 hex>] ]
```

所以 DSH 作为一个独立进程是**能**在运行时读到它的（端口同样从
`doInitServices completed, result: {"backendPort":…}` 那行拿）。附带两个代价：必须 **DuMate
客户端常驻**才有端口和 key；日志格式是当前版本（1.0.83.335）的实现细节，升级可能改。

插件**已经**接上 DuMate 的模型路由：读日志拿到本机端口与 `X-Dumate-Inapp-Key`，再用本地 shim 转发到
`http://127.0.0.1:<port>/api/qianfanproxy/v1/chat/completions`（上游本身就是 OpenAI 兼容，零协议转换）。
因此 DuMate 是**唯一强制要求客户端常驻**的模型平台——客户端关了就没有端口和 key，模型必然不可用。
DuMate 的签到则完全正常、且与此无关：它读客户端自己存的 cookie，调百度官方接口。

## Configuration reference

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `pythonCommand` | `python` | 驱动签到引擎的 Python 可执行文件 |
| `homeDir` | 内嵌的 `engine/` | 含 `adapters/` 与 `bridge.py` 的根目录 |
| `timeoutMs` | `180000` | 单轮超时 |
| `allowClaim` | `false` | 是否允许真实领取；`false` 强制只读 |
| `pushResult` | `true` | 手动跑完一轮后是否把摘要注入当前会话 |
| `statusRoute` | `/dsh-agent-checkin` | HTTP 状态端点的前缀 |
| `sessionsDir` | 空 | 会话日志根目录（用量统计的数据源）。留空则用 `$DSH_HOME/sessions` |
| `usageCacheSeconds` | `30` | 用量扫描的内存缓存 TTL（秒）；面板上的「刷新」按钮总是绕过它 |
| `traeProvider` | `false` | **仅首启种子**：TRAE 国内客户端的初始接入开关。权威在看板 `/dsh-agent-checkin/models` |
| `traeIntlEnabled` | `false` | **仅首启种子**：TRAE 国际客户端（同上） |
| `qoderCnEnabled` | `false` | **仅首启种子**：Qoder CN 客户端（同上） |
| `wbProvider` | `false` | **仅首启种子**：WorkBuddy 国内客户端（同上） |
| `wbProviderIntl` | `false` | **仅首启种子**：WorkBuddy 国际客户端（同上） |
| `modelRoutes` | `[]` | 要接进 DSH 的 provider 路由 |

`pythonCommand` / `homeDir` / `timeoutMs` / `allowClaim` / `pushResult` 这五个字段是
**hot-reload**（`volatile`）的：它们会出现在宿主的插件设置面板里，改完下一次运行立即生效，
不用重启宿主。`statusRoute` / `modelRoutes` 与上面五个 provider 开关不行，因为它们是
**注册期事实**——决定了要注册哪个 HTTP 路由、哪个 provider。把它们做成热改，界面会显示
「已关闭」而 provider 仍然挂着，那是假的，所以宁可要求重启。

`sessionsDir` 与 `usageCacheSeconds` 也不是 `volatile`：它们只被用量扫描器读一次
（扫描器在装配期创建，参数在那一刻定下来），所以改完需要重启宿主才生效。

榜单刷新的 TTL（6 小时）与榜单地址目前**不是配置项**，是 `lib/model-rank.js` 里的常量
（`DEFAULT_RANK_TTL_MS`、`LEADERBOARD_URL`）。它没有做成配置是因为改错了只会让面板更慢或
更容易失败，不会让结果更准——需要更勤地刷新时，面板上的「刷新榜单」按钮就是那条路。

每日定时的**时间不在这张表里**：它存在宿主 Schedule 的任务记录上，用
`/checkin-schedule on HH:mm` 管理。插件不去复制一份自己的「dailyTime」配置，因为那必然
和宿主里的真实任务表漂移成两份真相。

## Design notes

**为什么走子进程而不是原生移植？** 十个平台的凭证解密方式各不相同（Electron at-rest
AES-256-GCM、Chromium OSCrypt、纯 AES-CBC、Ed25519 签名、CDP 浏览器自动化）。这些实现
已经被真机跑过、打磨过，所以插件选择内嵌这份引擎的精选子集（`engine/`，MIT，© 2026 sole373）
而不是在 Node 里重写一遍——重写只会增加失败面，不会减少任何一块。插件的职责是调度与呈现。

**为什么不自己写 `LlmAdapter`？** 宿主已经自带 `@deepseek-ai/dsh-llm-pi-ai`，它负责
流式分块、工具调用增量、usage 归一、思考档位映射和图片额度。重写它等于重写一套流式
协议，**而且**要去抢同一个 LLM 注册位——宿主下次升级就会悄悄漂移。注册一条路由本质上
是配置问题，插件就当配置问题解决。

TRAE / Qoder / WorkBuddy 这三个本机客户端 provider 也用同一套 PiAiAdapter，规则不再弯折：
插件只在插件侧起一个 `127.0.0.1` 回环 shim（随机端口 + 随机 bearer），把各客户端的私有
协议翻译成 OpenAI 兼容的 `/v1/chat/completions`，PiAiAdapter 把它当成普通 OpenAI 端点调用。
协议翻译是配置之外的唯一代码，而且它必须存在——这些客户端根本没有可指的公开端点，凭证
住在已登录的桌面客户端里，不在某个 API key 里。凭据只留在进程内存与回环端口上，不新增
任何落盘 secret。
